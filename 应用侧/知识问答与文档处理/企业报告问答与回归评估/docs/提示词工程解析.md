## 1. 提示词的组装机制：`build_system_prompt`

```python
def build_system_prompt(instruction="", example="", pydantic_schema=""):
    delimiter = "\n\n---\n\n"
    # 指令 + Schema + 示例，用 --- 分隔拼接
    system_prompt = instruction.strip() + schema + example
```

系统提示词由三段拼成，顺序固定：**指令（instruction）→ JSON Schema → 示例（example）**。

每个提示词类都有**两个版本**：

| 版本 | 用途 |
|---|---|
| `system_prompt` | OpenAI 专用——调用 `chat.completions.parse` 时 schema 走原生 `response_format` 参数，提示词里只放指令+示例 |
| `system_prompt_with_schema` | IBM/Gemini 专用——这些 API 不支持原生结构化输出，**把 Pydantic Schema 的源码文本塞进提示词**，逼模型按文本 schema 输出 JSON |

`pydantic_schema` 的生成方式很巧妙（以 NamePrompt 为例）：

```python
pydantic_schema = re.sub(r"^ {4}", "", inspect.getsource(AnswerSchema), flags=re.MULTILINE)
```

用 `inspect.getsource()` 直接把 AnswerSchema 类的**源码**抠出来、去掉缩进，就是一段现成的 schema 描述文本——保证提示词里的 schema 和代码里的 schema 永远一致，改一处即可。

## 2. 五类问答提示词的共同骨架

四类 RAG 回答提示词（Name/Number/Boolean/Names）共享同一基座：

### 2.1 共享指令（`AnswerWithRAGContextSharedPrompt.instruction`）

```
你是一个RAG（检索增强生成）问答系统。
你的任务是仅基于公司年报中RAG检索到的相关页面内容，回答给定问题。
在给出最终答案前，请详细分步思考，尤其关注问题措辞。
- 注意：答案可能与问题表述不同。
- 问题可能是模板生成的，有时对该公司不适用。
```

三条提示词工程技巧集中在这里：

1. **范围限定**（"仅基于...检索到的内容"）——堵住模型用 parametric knowledge（训练记忆）答题的路，只允许用检索上下文；
2. **思维链前置**（"给出最终答案前，请详细分步思考"）——CoT，让推理过程显式化，既是答案质量保障，也是比赛要求的 reasoning_process 字段来源；
3. **问题可能无效的先验**（"模板生成的，有时不适用"）——比赛问题由程序随机生成，很多对公司无意义，提前给模型打预防针，为 N/A 答案铺路。

### 2.2 共享用户提示词模板

```
以下是上下文:
"""
{context}
"""

---

以下是问题：
"{question}"
```

`{context}` 由 `_format_retrieval_results()` 填入（步骤 6.3 的产物），`{question}` 是原问题。三段式 `---` 分隔符与 build_system_prompt 风格一致，帮模型区分结构。

### 2.3 统一的 AnswerSchema（四类的字段结构相同，类型/规则不同）

| 字段 | 设计意图 |
|---|---|
| `step_by_step_analysis` | **思维链主体**。Field 描述里写死"至少5步、至少150词"，并特别警告"注意问题措辞避免被迷惑；上下文里看似有答案，但可能只是相似值而非所问的值" |
| `reasoning_summary` | 约 50 词的浓缩摘要，供人工快速审核 |
| `relevant_pages` | 引用页码列表。Field 描述里定义了严格的收录标准："只包含直接包含答案或明确陈述的页面；不包含仅弱相关的页面；至少一页"——这就是步骤 7 引用校验的校验对象 |
| `final_answer` | 最终答案，类型随 kind 变化 |

这个四字段结构本身就是提示词工程：**让模型把"思考过程"和"最终结论"分开输出**，结论可以被程序精确抽取，思考过程可以被人审计。

## 3. 四类提示词各自的"反幻觉规则"

这是整个提示词体系最精妙的部份——每类的 `final_answer` 字段描述里写满了**负向规则**（什么时候必须答 N/A），因为比赛的评分核心就是"不该答的时候别瞎答"。

### 3.1 Number（数字类）——规则最严苛

`step_by_step_analysis` 的描述里内嵌了**指标匹配五步法**：
1. 明确问题中指标的精确定义；
2. 检查上下文中所有候选指标，"不要只看名称，要关注实际衡量内容"；
3. 仅当含义**完全一致**才接受（同义词可，概念不同不可）；
4. 明确列举四种必须拒绝的情况：范围不一致 / 代理指标 / 需要计算推导 / 聚合层级不匹配；
5. "有任何疑问，默认返回 N/A"——**不确定性原则**。

`final_answer` 描述里的格式规则：
- 百分比 `58,3%` → `58.3`；
- 括号负数 `(2,124,837)` → `-2124837`；
- 千单位要补零 `4970,5（千美元）` → `4970500`；
- **币种不符 → N/A**（如上下文是 USD 问题要 EUR）；
- **上下文不能直接给出（需计算）→ N/A**——如只有总分红和股数，问每股分红，必须答 N/A 而不是自己除。

这类规则的共同思想：**把"拒答"训练成模型的默认安全行为**，而不是让模型想方设法给出数字。

### 3.2 Boolean（布尔类）

思维链描述强调："有时上下文中看似有答案，但可能并非所问内容，仅为相似项"。
`final_answer` 定义了 True/False 与 N/A 的边界："上下文有相关信息但事情未发生 → False"（False 是事实性回答，不是缺信息）。

示例也体现这一区分：年报"提到年度分红金额增加，但政策未变"——问的是**政策变更**，答 False。这是典型的"相似信息陷阱"。

### 3.3 Name（单实体类）

`final_answer` 描述规定提取精度：
- 公司名 → 必须与问题中写法**完全一致**；
- 人名 → 必须全名；
- 产品名 → 必须与上下文中写法一致；
- "Without any extra information, words or comments"——杜绝"张三是CEO，他于2020年上任"这类啰嗦答案。

### 3.4 Names（多实体/名单类）

最复杂的提取规则：
- 问**职位变动** → 只返回职位名（不要姓名），同一职位多次变动只返回一次且用单数：`['首席技术官', '董事']`；
- 问**姓名** → 只返回全名：`['张三', '李四']`；
- 问**新产品** → 只返回产品名，且"候选产品或测试阶段产品不算新产品"；
- 无信息 → N/A。

即：**同一 schema 通过字段描述里的分支规则，适配三种语义不同的问题**。

### 3.5 Comparative（比较类）——另一条独立提示词

不走共享指令，单独设计（`ComparativeAnswerPrompt`）：
- 输入不是检索上下文，而是**各公司已算好的答案**（`process_comparative_question` 步骤③的 individual_answers）；
- 规则："只能基于已给出的答案，不可引入外部知识"；"答案必须与原问题公司名完全一致"；
- 排除规则："某公司数据币种不符需排除；全部排除 → N/A；仅剩一家 → 直接返回"。

### 3.6 Few-shot 示例

每类提示词都带 1-2 个手写示例（JSON 格式，含完整四字段）。示例不是随便举的：
- Number 给**两个**示例：一个正常取值的、一个该答 N/A 的（"研发设备原值"只有净值和累计折旧 → N/A），正反例配对；
- Boolean 示例专门演示"相似信息陷阱"（分红金额变 vs 政策变）。

## 4. 辅助提示词

### 4.1 RephrasedQuestionsPrompt（比较题拆解）

```
原始比较问题：'{question}'
涉及公司：{companies}
```

指令要求拆成"自洽、保持原意和指标、针对对应公司、表达方式一致"的单公司问题。
示例演示：`'2022年哪家公司营收更高，"苹果"还是"微软"？'` → 每个公司一句"X公司2022年营收是多少？"
**比较题的完整链路**：这道提示词生成子问题 → 子问题走标准 Number 流程 → ComparativeAnswerPrompt 汇总。

### 4.2 AnswerSchemaFixPrompt（JSON 修复）

当 IBM/Gemini 的输出不是合法 JSON 时，用模型自己修复：

```
系统：你是JSON格式化助手。回答必须以"{"开头，以"}"结尾，只能包含JSON字符串。
用户：下面是定义JSON对象Schema和示例的系统提示词: """{system_prompt}"""
     下面是需要你格式化为合法JSON的LLM原始输出："""{response}"""
```

技巧：**把原始系统提示词一起给修复模型**，它既知道目标格式又能对照修复。

### 4.3 RerankingPrompt（重排评分）

单块/多块两版，核心是定义了 **0-1 分、步长 0.1 的评分量表**，每个分数档都有文字锚点（0=完全无关, 0.5=一般相关, 1=完全匹配）。**评分量表离散化**比让模型自由打分更稳定。

## 5. 提示词在哪里被消费（api_requests.py）

```
_build_rag_context_prompts(schema)      # 步骤 6.4.1：按 kind 五选一，返回 (system_prompt, response_format, user_prompt)
    └─ use_schema_prompt = provider in {ibm, gemini}   # 决定用哪个系统提示词版本
send_message(...)                        # 6.4.2：user_prompt.format(context=rag_context, question=question)
    ├─ openai:  chat.completions.parse(response_format=AnswerSchema)     # schema 走参数
    ├─ gemini/ibm: schema 在提示词文本里 + json_repair + Pydantic 校验
    └─ dashscope: 纯文本，返回后兜底/解析（见 3.4 节改写）
```

## 6. 设计思想总结

| 技巧 | 在本项目中的体现 |
|---|---|
| 结构化输出（SO） | 四字段 AnswerSchema 锁死输出格式，结论可被程序精确抽取 |
| 思维链（CoT） | step_by_step_analysis 强制先推理后结论，且要求≥5步防敷衍 |
| 负向规则/拒答训练 | Number 类"有疑必 N/A"；四种必须拒绝的情形逐条列举 |
| Few-shot 正反例 | Number 一正一反；Boolean 演示相似信息陷阱 |
| 范围限定 | "仅基于检索内容"，堵 parametric knowledge |
| Schema 一致性 | inspect.getsource 抠源码，提示词与代码 schema 永不脱节 |
| 双版本提示词 | 原生结构化输出（OpenAI）vs 文本 schema（IBM/Gemini）按 provider 切换 |
| 评分量表离散化 | 重排 0-0.1-...-1 锚点式量表 |
| 自修复 | AnswerSchemaFixPrompt 让模型把损坏 JSON 修回合法格式 |
