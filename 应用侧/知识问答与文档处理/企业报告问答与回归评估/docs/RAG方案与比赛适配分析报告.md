# RAG-Challenge-2 方案解析与比赛适配性分析报告

> 从比赛规则出发，解释这套 RAG 方案为什么这样设计、为什么能拿高分；
> 并给出基于本工程向其他场景迭代升级的适配框架。

---

## 第一部分：比赛背景与规则拆解

### 1.1 比赛是什么

Enterprise RAG Challenge（ERC，第 2 轮 2025 年 2 月），主办方案例是真实的商业需求：
让企业级 RAG 系统**摄取一批上市公司年报，回答基于年报信息的问题**。
各家系统提交答案后由主办方人工评分。

### 1.2 规则中对系统设计有决定性影响的 6 条

| 规则 | 原文要点 | 对方案的约束 |
|---|---|---|
| ① 问题由程序随机生成 | "Question generator randomly pick files and generate random questions" | 问题措辞模板化、可能对该公司无意义；系统必须能识别并拒答 |
| ② 鼓励"无意义问题" | "Some questions don't make sense... 好系统应回答 N/A，坏系统会幻觉出看似合理的答案" | **评分核心 = 幻觉控制**，不是答题能力 |
| ③ 故意混入不存在的数据 | "questions include company names that are not included in PDFs — purpose is to detect hallucinations" | 公司路由必须先做存在性校验，答不了的必须 N/A |
| ④ 必须给出引用 | 答案需附 `pdf_sha1` + `page_index` | 检索结果必须带页码溯源，且引用必须真实（可抽查）|
| ⑤ 需要推理过程 | 提交格式含 `reasoning_process` | 纯"黑盒答案"不符合提交要求 |
| ⑥ 多公司比较题 | 如 "Which company has more liquidity?" | 需要跨文档的比较与汇总能力 |

另外题目类型分布（本仓库 erc2_set 真题）：number 58%、boolean 24%、name/names 各 9%——
**精确抽取型问题占绝对主体**，总结/开放型问题几乎没有。这个数字决定了
"重抽取、轻生成"的方案取向。

### 1.3 由规则推出的设计目标（优先级排序）

1. **不幻觉**（答不了的答 N/A）＞ 2. **答得准**（数字/人名精确）＞ 3. **可溯源**（页码引用真实）＞ 4. **可提交**（推理过程合规）＞ 5. 比较题能处理。

## 第二部分：该项目的 RAG 方案全貌

```
离线（建库）                          在线（问答）
─────────────────────────────        ─────────────────────────────────
PDF 年报                                问题 + kind(类型)
  │ Docling 解析(OCR+表格识别)           │
  ▼                                     ▼
结构化 JSON(文本/表格/图片按页归组)      ① 公司名路由(subset.csv 正则)
  │ 规整(页脚过滤/表格组/字符清洗)        ▼
  ▼                                    ② 检索: 每公司独立 FAISS 库
每页一段干净文本                         │   父文档检索(返回整页)
  │ 分块(300tok/重叠50)                  ▼
  ▼                                    ③ LLM 重排(向量分+LLM分加权)
chunk + 序列化表格块                     ▼
  │ DashScope embedding                  ④ SO CoT 回答(分步推理+引用页+答案)
  ▼                                     ▼
每公司一个 FAISS 索引                    ⑤ 引用校验(剔除幻觉页码)+落盘
```

七个关键技术点：

| # | 技术 | 解决什么问题 |
|---|---|---|
| 1 | Docling 深度 PDF 解析（OCR + TableFormer） | 年报是复杂排版文档，表格信息密度最高，普通文本抽取会丢表格语义 |
| 2 | LLM 表格序列化 | 把跨行/跨列表格拆成"上下文独立信息块"，单块被检索到时也能读懂 |
| 3 | 每公司独立向量库 | 检索按公司名路由到单一库，杜绝跨公司内容混入（配合规则③）|
| 4 | 父文档检索（PDR） | 命中 300-token 小 chunk 后返回整页，上下文完整，避免"断章取义" |
| 5 | LLM 重排 | 向量召回 30 候选 → LLM 相关性打分 → 加权融合取 top_n |
| 6 | SO CoT 提示词 | 四字段结构化输出：分步推理 + 引用页 + 最终答案，拒答规则写进提示词 |
| 7 | 引用校验 | 程序层兜底：LLM 给出的页码必须真实存在于检索结果中 |

## 第三部分：为什么这套方案高准确率适配比赛规则

逐条对应第一部分规则，说明方案组件与规则的因果关系：

### 3.1 对规则②③（防幻觉/N/A）——三层防线，这是夺冠的核心

```
第一层（提示词层）：SO CoT 的负向规则
  "指标含义不一致→N/A；需要计算→N/A；币种不符→N/A；有任何疑问默认 N/A"
第二层（路由层）：公司存在性校验
  问题中的公司名在 subset.csv 中匹配不到 → 直接报错 → N/A
  （实测："量子跳动"题正确返回 N/A）
第三层（程序层）：引用校验
  _validate_page_references() 剔除 LLM 幻觉出的、不在检索结果中的页码
```

多数参赛系统只有第一层（提示词），这套方案把防幻觉**下沉到了代码层**——
即使 LLM 不守规矩，幻觉页码也会被程序拦下。规则明确说"故意问库里没有的公司"，
路由层校验正是为这条规则量身定做的。

### 3.2 对规则①（模板化问题/措辞陷阱）——CoT 关注措辞

题目随机生成带来两类陷阱：
- **相似信息陷阱**：问分红政策变更，上下文有分红金额变化 → 提示词示例专门演示此陷阱，答 False；
- **概念近似陷阱**：问"原值"，上下文有"净值" → 指标匹配五步法强制语义比对，拒答。

`step_by_step_analysis` 要求"至少 5 步、150 词、特别注意问题措辞"，
本质是让模型把陷阱显式推理出来，而不是凭直觉秒答。

### 3.3 对规则④（引用真实）——引用校验 + 父文档检索

- PDR 保证返回给 LLM 的是**整页原文**，模型引用的页码天然来自真实页面；
- 步骤 7 校验后还做**兜底补齐**：引用不足 2 页时用检索 top 页补上——
  保证提交永远有合法引用，但绝不会出现指向不存在内容的引用。

### 3.4 对规则⑥（比较题）——分解-并行-汇总

"哪家公司研发投入更高"这种题，端到端直接答容易出错。方案把它拆成
标准 number 子问题（每家公司走一遍完整检索+SO CoT 流程），
最后用独立的 Comparative 提示词**只基于已算出的数字**做比较——
比较环节不接触原始文档，杜绝二次幻觉；币种排除规则也在此层处理。

### 3.5 对题目类型分布（58% 数字题）——解析质量优先

数字题的答案几乎都在表格里。链条 `Docling 表格识别 → 表格序列化 → 独立成块`
保证了"4970.5（千美元）"这类带单位的数值及其表头上下文能被完整检索到，
再配合提示词里的单位换算规则（千→补零、括号→负数），形成闭环。

### 3.6 适配性总结

比赛评分 = 幻觉率 + 准确率。这套方案的高明之处在于：
**把"防止系统自作主张"做成了系统性的工程**（路由校验 + 引用校验），
把"防止模型自作主张"做成了提示词工程（拒答规则 + CoT），
两者叠加，使 N/A 类陷阱题的失分率大幅下降；同时解析与检索质量
保证了正常题的准确率。

## 第四部分：基于本工程向其他场景迭代升级的适配框架

### 4.1 先回答你的问题：这是不是"为不同场景设计不同 RAG 方案"？

**是，但不完全是重新设计。** 更准确的模型是：

> RAG 是一个固定骨架（解析→切块→索引→检索→重排→生成→校验），
> 每个场景的差异体现在**七个可替换的"策略插槽"**上。
> 本工程的七个技术点，每个都是某个插槽在比赛场景下的"最优解之一"，
> 换场景时按决策表替换插槽即可，骨架代码可直接复用。

### 4.2 七个插槽的适配决策表

| 插槽 | 本工程的选择 | 换场景时考虑什么 | 典型替代方案 |
|---|---|---|---|
| ① 文档解析 | Docling（复杂 PDF 年报） | 数据源形态：网页/Word/Markdown 不需要 Docling；扫描件需要 OCR；代码仓库用 AST | Unstructured、trafilatura、自研爬虫+清洗 |
| ② 内容增强 | LLM 表格序列化 | 信息密度在哪：法规条文（条款编号）、代码（函数签名）、FAQ（问答对） | 表格→图结构、代码→符号索引、条款→层级路径 |
| ③ 索引组织 | 每公司独立库 | 是否需要权限隔离/多租户；知识是否频繁更新 | 单库+元数据过滤、增量索引、图数据库 |
| ④ 检索粒度 | 小 chunk 召回 + PDR 返回整页 | 答案上下文窗口需求：短答案（词条）用 sentence 粒度；长答案（合同条款）用段落/章节粒度 | 句子级、块级、章节级、Agentic 迭代检索 |
| ⑤ 重排 | LLM 加权融合 | 成本/时延预算：低延迟场景用 BGE/Cohere reranker（快、便宜）；高精度场景保留 LLM 重排 | 交叉编码器、BM25 混合、无重排 |
| ⑥ 生成策略 | SO CoT + 拒答规则 | 场景的目标函数：**防幻觉优先**（本工程）→ 保留；**召回优先**（客服）→ 放宽拒答、加"根据资料推测"话术；**创意生成** → 换开放提示词 | 直接生成、引用优先生成、多答案聚合 |
| ⑦ 输出校验 | 引用页码校验 | 需要什么样的可审计性：医疗/法律要逐句溯源；内部分析只要结论 | 事实一致性校验（NLI）、数字对账、人工审核队列 |

### 4.3 三个典型迁移示例

**A. 企业知识库问答（内部制度/流程）**
- 保留：骨架 + SO CoT + 引用校验（员工需要看到出处）；
- 替换：① 解析（多数是 Word/PDF 简单排版，Docling 可降级为 pypdf）；③ 改为单库+部门元数据过滤；⑥ 拒答规则放宽为"资料不足时说明缺失并建议联系部门"（服务导向，不是考试导向）。

**B. 智能客服（产品文档 + 历史工单）**
- 保留：检索+重排骨架；③ 按产品线分库；
- 替换：⑥ 生成策略改为"答案+操作步骤+相关工单链接"，允许合理推测并标注置信度；⑦ 校验改为满意度兜底而非引用校验；⑤ 换 BGE reranker 满足毫秒级响应。

**C. 金融研报分析（延续本场景但换要求）**
- 若目标是"跨公司对比分析"而非单点抽取：保留全部，重点升级④（比较题路由）为多文档并行检索的 Agent 编排；
- 若接入实时行情：新增插槽"知识新鲜度管理"（时间感知检索，旧年报降权）。

### 4.4 落地迭代建议（针对本代码库）

1. **配置化**：七个插槽已基本是独立类（PDFParser / TextSplitter / *Retriever / LLMReranker / APIProcessor），
   下一步可做策略注册表（按场景配置组合），而不是改代码；
2. **评测先行**：每个场景先造 20-50 道带标准答案的题（如 my_set 的做法），
   再动方案——本工程的可贵之处就在于它证明了"先造题、再验证"的闭环可行；
3. **记录失败案例**：把幻觉/答错的题加入回归测试集，这是持续提升准确率的最短路径。
