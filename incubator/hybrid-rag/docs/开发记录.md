## 2026-11-24 · 真实容器验收

- Windows Docker Desktop 28.5.1，Linux x86-64，Intel Core i3-12100F，Docker 可用内存约 7.68 GiB，每个模型 CPU 线程配置为 2。首次构建使用网络，主模型文件合计约 4.54 GB。
- D1 `BAAI/bge-m3@5617a9f61b028005a4858fdac845db406aefb181` 完成真实 CPU 预热。[编码冒烟](../sample/check_encoder.py) 验证同批的 `/encode`、`/dense` 和 `/sparse` 输出一致、dense 归一化、稀疏 token ID 唯一且有序，以及超过 1024 token 返回 422。
- D3 Java 使用真实编码器从空 `rag_chunks` 导入 4 个文件、5 个切片。直接回读 Qdrant payload 核对退款 PDF 第 1、2 页各有独立点 ID，页码和原文一一对应。
- D4 `BAAI/bge-reranker-v2-m3@953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e` 与编码器在同一次 Compose 启动中完成加载和预热。请求「退款批准后多久能退回原支付渠道？」返回 5 条证据，首条为 `policies/refund.pdf` 第 2 页，`scoreType=reranker`，`hits` 与 `citations` 中的 `chunkId` 均为 `a3c4071f-4598-3fae-8460-8c75b02fa460`。
- 分别用 `--network none`、只读模型缓存卷和 `HF_HUB_OFFLINE=1` 实例化两种模型并完成真实预热。随后以 `HF_HUB_OFFLINE=1` 和 `--pull never` 启动完整 Compose，导入任务验证并复用原快照的 5 个点。
- 暂停重排容器后查询 `TKT-8472`，30.07 秒后 API 返回 `rerankDegraded=true`、`scoreType=rrf`，命中点和顺序与关闭重排的对照请求一致。随后恢复容器。
- 重启 Qdrant 后导入任务再次核对并复用 5 个持久化点。评估开关恢复默认关闭，检索 API 和两个模型容器均就绪。再次查询退款问题，编码、重排和 Java 日志记录同一请求 ID，第一条仍引用原来的 PDF 第 2 页点。

```powershell
docker run --rm --network hybrid-rag_default -v "${PWD}/sample:/sample:ro" python:3.11.14-slim-bookworm python /sample/check_encoder.py
```

`RAG_EVALUATION_ENABLED=true` 时运行 `python sample/evaluate.py`。四条正例参与 Recall@5 与 MRR@5；一条受控无匹配查询验证空命中。每种路径预热一次，再执行 3 轮共 15 个请求，统计端到端 p95。

| 检索路径 | Recall@5 | MRR@5 | p95 毫秒 |
| --- | ---: | ---: | ---: |
| Dense | 1.000 | 1.000 | 347.1 |
| Sparse | 1.000 | 1.000 | 298.0 |
| RRF | 1.000 | 1.000 | 351.9 |
| RRF + 模型重排 | 1.000 | 1.000 | 3101.4 |

这组 5 切片样本用于功能回归。四种模式均命中所有正例，重排增加了约 2.75 秒 p95 延迟。相关性排序收益和索引性能需要更大标注语料衡量。[评估查询](../sample/queries.json)
