# 开发计划

日期：2026-11-24。当前设计见 [MVP 设计](MVP设计.md)，实际进展见 [开发记录](开发记录.md)。以下阶段按顺序推进，不需要先搭出所有模块。

工程实现遵循 [技术实现方案](技术实现方案.md)：按场景约束选择技术，先落实可读的边界与测试，再逐步增加功能。

## 开发顺序

| 阶段 | 具体工作 | 过程交付 | 完成条件 |
|---|---|---|---|
| D0：定方案 | 固定首个任务、功能范围、模块、停止语义与验收 | 设计文档、示例输入/任务/预期结果 | 文档与示例一致；本次已完成 |
| D1：跑通最短链路 | 创建 Python 3.12 包、共享契约与 CLI；模拟模型、两工具和正常循环；落实 uv、类型/格式检查和项目 CI | 可运行的离线 demo、正常链路测试、锁文件与质量配置 | 模拟模型完成读写与最终回答；环境可复现，已实现部分通过静态检查 |
| D2：可靠停止 | 加模型调用/工具调用/总时长预算、输入限额、Ctrl+C 和失败收尾 | 边界测试、停止原因 | A02–A09 相关场景通过，不再发起超限动作 |
| D3：可追溯与可验收 | 加 JSONL、结果摘要、预期快照、自动验收及 show/verify | 一次完整离线运行记录、覆盖率和平台检查报告 | A01–A12 验证通过；自动/手工和平台跳过逐项标明，结果错误不会报通过 |
| D4：接入真实模型 | 在同一接口下增加可选 HTTPX 适配器；配置模型与地址；关闭隐式重试 | 配置示例、离线 HTTP 适配测试、在线验收记录 | 模拟测试仍通过；真实任务执行和取消分别留证 |

D1–D2 是开发中的中间状态，只有 D3 具备四项完整能力；D4 验证实际模型可用性。此处不预估未经验证的工期。

## 每个阶段都按这个小流程交付

1. **读当前状态**：先读开发记录，检查 Git 状态和远程差异，不覆盖其他任务的修改。
2. **选一条用户流程**：明确本阶段输入、输出和通过条件，不顺手扩展长期能力。
3. **写最少代码**：优先函数与普通数据结构，新增抽象必须解决当前问题。
4. **验证这条流程**：正常场景加相关失败场景。运行时测试使用标准库 `unittest` 和模拟模型，不依赖付费服务。
5. **留下记录**：在开发记录追加实际修改、执行命令、结果、未验证项和下一步；完成后再勾选。
6. **同步仓库**：更新相关入口，执行维护检查，选择性提交并 push；fetch 后复核本地与远程哈希和工作区。

开发时从仓库根目录运行维护检查：

```powershell
python scripts/maintain.py index
python scripts/maintain.py check
git diff --check
```

项目实现 D1 后，再补上经过验证的安装、测试和演示命令。README 中当前展示的是目标 CLI，不能提前登记为已跑通。

每次实现按技术方案执行 Ruff 格式与规则检查、mypy 严格类型检查及相关测试；D3 完整 MVP 使用分支覆盖测量且项目覆盖指标至少 85%，关键停止与失败场景必须有用例。检查只作用于本孵化项目，不批量改写历史案例。
